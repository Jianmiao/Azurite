# Normal settings lifecycle policy — preparation only

This is one additive managed component for the next normal Catalog increment. It does not install hooks, start AA, create native owners/sessions/iterators, set native readiness/dirty flags, or provide normal-launch permission. An external admission lease is mandatory on every transition; no production permitting implementation is supplied. A null lease fails closed. Fixture leases exist only in the test project.

The existing route-selftest `ProbeLedger` and its normal-mode refusal remain unchanged. This project references the already-frozen `Azurite.EditorIsolation.Policy.LabOnly.dll` for the exact `RunPaths` and `WindowsFileIdentity` types. It does not reference/build the old project. Tests reference this new production project and exercise its actual filesystem snapshot reader on new C: fixtures. The frozen legacy DLL must be present; there is no fallback copy of its policy logic.

## Bounded design decision

The ledger binds one canonical run ID, controller binding generation, current PID, native thread ID, actual managed callback thread, and observed native owner. InitTask, ReadUserSettings and SaveTask iterator pointers are observation identities, not objects allocated by this component. All callbacks carry a monotonic observation sequence; stale run/generation/owner/data/path/thread/sequence evidence fails and latches the ledger closed.

Valid startup begins with capture of the existing state-0 InitTask coroutine argument during the bound Awake. Its actual state-0 MoveNext entry receives an immutable invocation identity; the matching original return must yield true/state 1 and identify the actual ReadUserSettings child. Only that child may enter the original read. After its successful false return binds the original data, the same InitTask may enter state 1 with false readiness. Its invocation remains active until the matching original terminal return. Missing, foreign, stale, duplicate, exceptional and out-of-order callbacks fail closed.

Resource.Initialize is observed as its own callback boundary. False readiness is valid only with the active bound state-1 invocation token and before readiness has been observed true. A later direct true-ready resource callback remains valid after initialization; a true-ready callback within the continuation must carry that live token. At most one initial resource entry is recorded. No resource observation is invented when no callback occurs, and observation grants no cache/resource admission.

The authentic state-0 SaveTask argument is captured at the qualified coroutine-start prefix during that same active continuation, with true readiness. Capture itself may supply the first true-ready observation; an invented earlier ready event is unnecessary. The initial SaveTask wait may finish before InitTask returns, or execute after its return. Initialization completes only on the original InitTask false return with terminal state -1, correct owner/data, observed true readiness, captured saver, and no unfinished nested save frame. Later state-1 save resumes, writes, lifecycle success and close require that completion.

`InitMoveNextReturned`'s `yieldedReadIterator` parameter describes an object actually yielded by a true return; pass zero on the terminal false return. It does not claim that the native iterator clears its retained current field. Invocation tokens are reference-identity capabilities minted by this ledger, not caller-constructed native frames. The adapter must pass the live token only for genuinely nested callbacks and call `Fail` plus the separately required fatal refusal path on an original native exception; it must never report that exception as a normal return.

There are no `OnReadyEntered`/`OnReadyReturned` events in this contract. Existing static evidence places the indirect native dispatch at RVA `0x7f21f2`, its normal continuation at `0x7f21f4`, and the ready store at `0x7f21fb`; its null branch also proceeds to readiness. That timing is static evidence, not an observed callback boundary. The policy does not claim that a non-null event fired, that a particular subscriber caused Resource.Initialize, or that all subscribers ran. An ordinary-entry adapter can preserve the original InitTask body and observe the boundaries above without an instruction-site patch, sentinels, or manual coroutine advancement. See `.superpowers/sdd/azurite-authoring-20261108/normal-editor-native-adapter-boundary.md` for the precise capture seams and remaining qualification.

The bound SaveTask must first execute state 0 and yield state 1. Subsequent state-1 resumes may be clean or dirty. A dirty resume must contain exactly one matching native WriteUserSettings entry/return. Fresh path/file/hash validation runs at every write entry, after the original write return, and again before committing that write at the enclosing SaveTask return. Accepted counters and hash lineage commit only when the enclosing original SaveTask return is valid, yielded true and returned to state 1. No refusal is counted as a completed write/cycle. Reentrant callbacks and stale/foreign invocation or write tokens are rejected.

Native details were resolved only from local existing evidence: `GameAssembly-100689392.asm.txt` enters state 0 without writing, checks dirty in state 1, calls WriteUserSettings at `0x7f2662`, then returns true/state 1. `GameAssembly-100691301.asm.txt` deletes bk.3, moves bk.2→bk.3 and bk.1→bk.2, and replaces main with backup bk.1. The accepted CLI-positive run's saved inventory confirms first bk.1 hash equals its original seed hash `29ed8483c6ff3bffd1a11ca0751c43ea36fda93da89c3122d3862c5c6a2c02be`; that one write is not relabelled as repeated normal-runtime proof.

Accordingly, the managed hash lineage expects new bk.1=previous main, bk.2=previous bk.1, bk.3=previous bk.2; control-seed bytes remain fixed. Repeated identical-content saves are allowed. The reader admits only the main/control and contiguous bk.1..3, rejects reparses/hardlinks/unknown sidecars, bounds each file to 1 MiB, and validates persisted workspace/cache paths. It reads fresh snapshots; it does not perform native saves or hold read locks across an original native write.

**Carried-forward P3 limitation:** the per-file byte limit does not bound directory-enumeration work. The reader enumerates and sorts the entire settings directory before validation and again for the final comparison, with no entry-count or total enumeration/sort memory cap. This component does not provide bounded hostile-directory scanning. That existing limitation is unchanged by the InitTask contract alignment.

This is not an OS transaction, same-account adversary boundary or proof that supplied callbacks really came from native code. The future adapter must authenticate native method/field/class identity and hits, scope Awake/coroutine-start capture to the actual owner, validate iterator owner/class/state, establish actual InitTask→read-child/SaveTask ownership, preserve original bodies, provide the independent normal admission/consumer-exclusion contract and synchronously terminate the owned child on refusal. The shared native coroutine-start RVA is identified, but its exact overload/MethodInfo identity remains to be qualified separately. Hash lineage does not distinguish an attacker recreating identical bytes, and the component does not prove actual disk writes when content is identical.

The component's repeated-save observation property is only a managed sequence result. It does not establish Catalog stability, OS/cache/resource/NoSound/discovery isolation, native bindings, integration, graceful exit or ordinary Editor acceptance. Those gates remain separately required and unprovided here.

## Build and test scope

Build the new test project with `dotnet build AcceptanceHarness/NormalEditor.Tests/NormalEditor.Tests.csproj -c Release`; its only project reference is the new policy. The frozen existing policy binary above is a required read-only dependency, not an automatically rebuilt project. The final checked build used the same command with `--no-restore` after the initial restore.

Run the source-linked console tests with `dotnet AcceptanceHarness/NormalEditor.Tests/bin/Release/net6.0/NormalEditor.Tests.dll <fresh-ignored-C-fixture-directory>`. The aligned suite has 102 passing tests, build 0 warnings/errors. It retains the repeated-save/freshness/refusal-counter checks and adds InitTask invocation/read-child identity, early and late resource observation, nested initial saver wait, missing/exceptional/foreign/stale completion, and readiness-regression controls. All owner/data/iterator values are managed observation fixtures; filesystem checks use actual new C: files. No native AA object, session, coroutine or readiness flag is created or assigned. The test-only admission lease is not shipped by the policy library.

The reviewed v1 package remains under `NormalEditor.Tests/artifacts/`. The v1 eight-source/two-output checkpoint, original manifest, new build/test logs, failed controls, base-to-new scoped diff and source/output hash manifest are under `artifacts/normal-editor-inittask-alignment-20261108-3a4b77e462ab413eb7f6bd29547a0882/`. Review artifacts are not launch approval.
